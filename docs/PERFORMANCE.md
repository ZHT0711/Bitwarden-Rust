# 性能测量

性能结果按操作、构建配置和数据规模记录，不能将一项微基准的改善当作整个桌面端已达到最佳性能。

## 保险库写入后的本机投影

运行：

```powershell
./scripts/measure-vault.ps1
```

默认采用 Release 构建。脚本使用应用的原生构建工具链，并显式运行平时忽略的 `measure_confirmed_write_projection` 测量；不需要真实账户或服务器。

数据来自官方 SDK 的公开合成账户，分别创建 100、1,000、10,000 个经过 SDK 加密的登录条目。每组预热 3 次，记录 25 次操作，报告中位数和 P95。测试重复投影同一个条目，名称保持不变，对应收藏或附件变更等不需要重新排序的场景；没有发出真实写入请求。计时覆盖服务器确认写入之后的本机列表元数据投影与返回概览的克隆；加密测试数据、网络、磁盘快照、JSON/ABI 传输和 WinUI 渲染不在计时范围内。生成的密码、密钥和完整条目内容不会写入测量日志。

测量测试没有固定耗时断言，避免共享 CI 机器的调度波动造成误报。正确性由常规 Rust 测试与实际 DLL 互操作测试单独检查。比较结果必须使用同一机器、同一构建配置、相同数据规模与采样方式。

## 2026-11-22 本机结果

环境：Windows x64，AMD Ryzen 7 H 260（8 核 / 16 线程），Rust 1.100.0，默认 Release 优化。基线为 `3d03742` 的生产代码加同一测量测试，优化后使用相同数据规模与采样方法。

| 条目数 | 原实现中位数 | 增量实现中位数 | 原实现 P95 | 增量实现 P95 |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 1.9177 ms | 0.0707 ms | 2.5351 ms | 0.0718 ms |
| 1,000 | 17.6834 ms | 0.4325 ms | 19.9740 ms | 0.5671 ms |
| 10,000 | 177.7321 ms | 3.5112 ms | 195.7673 ms | 4.4090 ms |

10,000 条场景下，本机投影中位耗时减少约 98.0%，约为原来的 1/50.6。该比例仅适用于上述局部测量，不能推算为完整保存操作或界面的加速比例。

集成 Windows Hello、TOTP 登录兼容和文本 Send 后重新运行了同一 Release 测量；100、1,000、10,000 条中位数分别为 0.0240、0.1452、2.9223 ms，P95 分别为 0.0246、0.1512、4.7747 ms。未同时重测基线，这组数据用于确认当前版本的局部性能，不作为新的加速比。

原实现每次单条目写入后都克隆全部密文、调用 SDK 解密全部列表元数据并重新排序。新实现只对已确认的条目运行同一套严格解密与显示投影，再更新其概览位置；名称未变时直接替换原位置。永久删除先确认 SDK 仓库已移除对应密文，再移除其显示元数据。按条目记录的解密失败集合保证修复或删除损坏条目后仍能正确计数。完整同步、离线解锁仍重建全部概览。密文快照直接收集列表，避免先复制整张哈希表和字符串键。

概览查找、返回概览的克隆，以及删除时的列表压缩仍随条目数增长。当前 ABI 与界面继续接收完整概览，尚未改成增量传输。

## 2026-11-23 文件夹索引专项优化

```powershell
dotnet run --project tests/Bitwarden.Interop.Tests -c Release -- --measure-folders
```

使用实际 `FolderHierarchy.Build`，仅构建非敏感合成文件夹和列表元数据，不启动 WinUI、不访问账户。每个场景预热 3 次、采样 25 次；计时覆盖排序、路径索引、显示名、父子数组、遍历与计数。输入字符串及条目在计时之前建立，校验在计时之后执行。分配量使用 `GC.GetAllocatedBytesForCurrentThread` 的单次构建差值，不代表进程常驻内存或峰值；P95 为排序后的第 24 个样本。没有固定耗时断言。

同一 Windows x64、AMD Ryzen 7 H 260、.NET SDK 10.0.404 / Release，完全相同的测量代码与输入；原实现 SHA-256 为 `FA2BCE7285F5F09C20CF34A3AD2D34EB8B5B0FE6685E6048BD70495E9B0FFDD5`（本机快照 `work/folder-hierarchy-prefix-baseline.cs`）。原 / 新日志为 `work/folder-index-baseline.log`、`work/folder-index-optimized.log`，输入与源文件摘要见 `work/folder-index-evidence.json`。

| 场景 | 原中位数 ms | 新中位数 ms | 原 P95 ms | 新 P95 ms | 原分配 B | 新分配 B |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 段缺失路径，无父节点 | 0.4015 | 0.0019 | 0.8242 | 0.0139 | 2,115,816 | 2,472 |
| 512 段缺失路径，连接真实父节点 | 0.3984 | 0.0037 | 0.5452 | 0.0089 | 2,132,512 | 10,936 |
| 2,048 段缺失路径，无父节点 | 4.9906 | 0.0019 | 6.9144 | 0.0042 | 33,622,248 | 2,472 |
| 2,048 段缺失路径，连接真实父节点 | 4.4824 | 0.0120 | 5.3973 | 0.0223 | 33,688,096 | 35,512 |
| 10,000 个平面文件夹 | 5.6685 | 5.1810 | 9.9539 | 6.7504 | 4,483,000 | 3,741,360 |
| 1,000 层真实链，名称共 1,000,000 字符 | 4.5027 | 3.7325 | 5.8333 | 4.4153 | 2,668,768 | 583,456 |
| 10,000 个文件夹 / 条目，100 个根分支 | 12.3319 | 7.4794 | 22.4830 | 22.4568 | 4,988,288 | 3,850,648 |

两种缺失路径场景均只有 2 个真实文件夹；2,048 段输入分别共 16,394 / 16,401 字符。原实现逐层截取并哈希前缀，产生约 33.6 MB 临时分配；新实现按 Ordinal 路径排序，用字符前缀栈复用最近真实父节点，只有显示名需要一次切片。字符前缀不等于 `/` 祖先（如 `A/B` 与 `A/BC`）；非分段匹配时沿候选的已知真实父节点连接，避免标点、重复分隔符与同名路径改变归属。候选各进出栈一次，不再为缺失的每一级分配长前缀；排序仍有字符串比较成本，未声称整个构建为常数时间。

页面仍按概览建立一次层级和计数，搜索复用索引。展开序列、子树计数与面包屑保持迭代处理，不生成虚拟 UI 父节点、不改原名 / ID、不改变条目精确归属或只读权限。新增独立全候选参考算法对照 100 组随机快照及反序输入，并覆盖 8,192 段缺失路径（一次构建分配小于 1 MB）与万级分支树；此前 1,000 层模型检查保留。

上述是局部模型测量。新 MSIX 的 47 项实际 UI 回归确认已有导航、非级联修改和离线权限未退化，但不是万级 / 千层 UI 压力测试。极短微秒样本、JIT / GC 与本机调度影响耗时，不据此宣称完整界面加速比例；长路径布局、实际大库 WinUI 响应和内存峰值仍需独立验收。
